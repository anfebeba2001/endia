# Implementation Plan: Endia MVP — E2E Learning Loop

**Branch**: `feature/endia-mvp` | **Date**: 2026-09-09 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/mvp-e2e/spec.md`

## Summary

Validate the core learning loop end-to-end: user enters a theme → gets subtopic suggestions → reads knowledge snacks → answers a quiz with plausible distractors → sees results + XP stub. Backend is a Spring Boot 3.4.x REST API with layered architecture (domain/application/infrastructure/interfaces), MySQL 8.x persistence, and an LLM abstraction layer (`LlmProvider`). Frontend is Angular 19+ with standalone components and signals. No auth, no gamification beyond an XP stub returned in API responses.

## Technical Context

**Language/Version**: Java 21 (backend), TypeScript 5.x (frontend)

**Primary Dependencies**:
- Backend: Spring Boot 3.4.x, Spring Data JPA, Hibernate 6.x, Spring Web (REST), Spring Validation (Jakarta), RestClient (Java 21 built-in)
- Frontend: Angular 19+, Angular Signals, Angular Router, HttpClient

**Storage**: MySQL 8.x — single database, no H2/SQLite in any environment. DDL auto-generated by Hibernate in dev (`spring.jpa.hibernate.ddl-auto=update`).

**Testing**: JUnit 5 + Mockito (unit), Spring Boot Test + Testcontainers MySQL (integration), Angular Karma/Jest (frontend unit)

**Target Platform**: Linux server (backend), modern browsers Chrome/Firefox/Safari latest 2 versions (frontend)

**Project Type**: Web application (monorepo: `backend/` + `frontend/`)

**Performance Goals**: API responses within 500ms of backend processing time (excluding LLM latency). Full E2E flow under 60s wall-clock time (excluding LLM latency).

**Constraints**: No authentication in MVP. All requests anonymous. LLM calls via OpenAI-compatible API (configured via `LLM_API_KEY` and `LLM_BASE_URL` env vars). Quality gate must reject bad quiz questions before serving.

**Scale/Scope**: Single-user MVP validation. No concurrent user scaling requirements. 5 JPA entities, 5 REST endpoints, 1 Angular frontend.

## Architecture Decisions

### 1. Domain Entities Use UUID Primary Keys
All entities use `java.util.UUID` as primary key (stored as `CHAR(36)` in MySQL). This avoids auto-increment ID leakage and is future-proof for distributed systems. Tradeoff: slightly larger index size vs. global uniqueness guarantee.

### 2. JSON Columns for Variable-Length Lists
`Snack.related` (List<String>) and `QuizQuestion.options` (List<String>) stored as MySQL JSON columns via `@Convert(converter = JpaJsonConverter.class)`. This avoids join tables for inherently atomic data that is always read/written as a whole. Tradeoff: no per-element querying (not needed in MVP).

### 3. API DTOs vs Application DTOs
Two layers of DTOs: **API DTOs** in `interfaces/rest/dto/` (shape what the REST API returns) and **Application DTOs** in `application/dto/` (shape what services consume/return). This allows the API layer to evolve independently from service logic. Tradeoff: more files (acceptable for clarity).

### 4. Prompts Externalized as Markdown Files
LLM prompts stored in `resources/prompts/*.md` and loaded via `@Value` or classpath resource reading. This keeps prompts versionable, readable, and testable without touching Java code. Tradeoff: requires a file-loading mechanism (simple Spring resource loading).

### 5. Quality Gate as Separate Application Service
`QuizQualityGate` is a standalone service (not embedded in `QuizService`) so it can be unit-tested in isolation and potentially reused for other generated content. This follows SRP. Tradeoff: one more class (negligible cost for testability).

### 6. No Auth / No User Entity
MVP has no authentication. All requests are anonymous. No `User` entity exists. XP is calculated and returned in responses only — never persisted. When auth is added post-MVP, a `User` entity and session management can be layered in without restructuring existing entities.

## Testing Strategy

### Unit Tests
- **QuizQualityGate**: Feed intentionally bad questions (duplicates, empty, too short) → verify rejection. Feed valid questions → verify pass.
- **QuizService**: Mock `LlmProvider`, verify XP calculation, shuffle logic, re-roll behavior.
- **ThemeService**: Mock `LlmProvider` and repositories, verify flow orchestration.
- **SnackService**: Mock `LlmProvider` and repositories, verify snack generation and persistence.

### Integration Tests
- **ThemeFlowIntegrationTest**: Full theme → subtopics flow with Testcontainers MySQL.
- **QuizFlowIntegrationTest**: Full quiz generation → answer → summary flow with Testcontainers MySQL.
- **OpenAiLlmProviderTest**: Test HTTP client against mock server (WireMock or MockWebServer).

### Frontend Tests
- **Component unit tests**: Each page component tested with mock services.
- **Service tests**: HTTP client mocked, response mapping verified.

### Manual E2E
- Start backend + frontend locally, complete full flow via browser.
- Verify all acceptance scenarios from spec.md manually.
