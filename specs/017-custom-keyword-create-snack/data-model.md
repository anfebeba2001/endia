# Data Model: "Create snack" from a Custom Keyword's Generated Meaning (Task 12)

**Feature**: `017-custom-keyword-create-snack`

**Persistence**: **NO schema change. NO entity change. NO migration.** The created snack is a
feature-014 `MeaningSnack`, persisted through the existing `POST /api/meaning-snacks/generate` path.
The project has **no Flyway/Liquibase**; schema is managed by Hibernate
`spring.jpa.hibernate.ddl-auto=update` (`backend/src/main/resources/application.yml`). Because no
entity or column changes, `ddl-auto=update` issues **no DDL** for this feature.

This document therefore records only the **frontend UI value types / state** introduced or reused by
the feature, plus the reused persisted model for reference.

---

## 1. Reused persisted entity (backend — unchanged)

### 1.1 `MeaningSnack` (`com.endia.domain.model.MeaningSnack`) — reused as-is

The created snack is exactly this existing aggregate (feature 014). No field is added or changed.

| Column | Type | Notes |
|--------|------|-------|
| `id` | UUID (PK) | |
| `theme_id` | UUID (FK → `theme`) | resolved from the current theme |
| `source_subtopic_id` | UUID (FK → `subtopic`) | **the Option-A source**: regular `subtopicId` or meaning `sourceSubtopicId` |
| `source_term` | `VARCHAR(500)` | the custom term (trimmed); a feature-016 term (≤10 tokens) fits comfortably |
| `source_definition` | `VARCHAR(200)` | the generated meaning, normalized to ≤20 tokens / ≤200 chars by the service |
| `concept` / `metaphor` / `why_it_matters` | `TEXT` | generated by the reused LLM flow |
| `related` | `JSON` | generated related terms |
| `kind` | `VARCHAR(20)` | always `MEANING` (the quiz-free discriminator) |
| `created_at` | `DATETIME` | set on persist; listing order |

Unique index `ux_meaning_snack_source (source_subtopic_id, source_term)` — the **dedup key** reused by
this feature (case-insensitive idempotent generate).

**No quiz fields exist** on the entity: a meaning snack is structurally incapable of carrying a quiz
(FR-011).

## 3. Frontend UI state / value types

All new state is in-memory and additive; none is persisted.

### 3.1 Captured source subtopic (existing signal, newly populated for the custom flow)

```ts
// SnacksComponent — private signal, existing (feature 014)
private readonly activeKeywordSubtopicId = signal<string | null>(null);
```

| Card mode | Value written | When |
|-----------|---------------|------|
| Regular highlighted keyword | active regular entry's `subtopicId` | `openKeyword(...)` (existing, unchanged) |
| **Custom-Define** | active entry's source subtopic: regular → `subtopicId`; meaning → `sourceSubtopicId`; none → `null` | **`onDefineRequested()` (new)** |
| Cleared | `null` | `closeKeyword()` (existing) |

Resolution expression (new, in `onDefineRequested`):

```ts
const entry = this.currentEntry();
const sourceSubtopicId =
  entry?.kind === 'regular' ? entry.subtopicId
  : entry?.kind === 'meaning' ? entry.sourceSubtopicId
  : null;
this.activeKeywordSubtopicId.set(sourceSubtopicId);
```

This is the single source of truth for both the dedup key and the generate request's `subtopicId`
(FR-005).

### 3.2 Custom-keyword card view model (existing, reused)

The generated definition from feature 016 is fed into the existing card as a `SnackKeyword`:

```ts
// models/snack.model.ts (existing, unchanged)
export interface SnackKeyword {
  term: string;       // custom term (plain, untrusted)
  definition: string; // generated meaning (≤20 words, plain, untrusted)
}
```

| Card state | `activeKeyword` | `definitionLoading` | `definitionError` | `generateEnabled` | action label |
|------------|-----------------|---------------------|-------------------|-------------------|--------------|
| Defining | `{ term, definition: '' }` | `true` | `null` | `false` | — (no action) |
| Meaning ready | `{ term, definition: generated }` | `false` | `null` | `true` (captured subtopic) | `Create snack` |
| Definition failed | `{ term, definition: '' }` | `false` | user-safe message | `false` | — (no action) |
| Creating | `{ term, definition: generated }` | `false` | `null` | `true` | `Creating…` (loading) |
| Created | `{ term, definition: generated }` | `false` | `null` | `true` | `Added to your snacks` (done, disabled) |
| Already existed | `{ term, definition: generated }` | `false` | `null` | `true` | `Added to your snacks` (done) via `hasGenerated` |

### 3.3 Card input (additive)

```ts
// KeywordDefinitionCardComponent (additive; default false → feature-013/014 surfaces unchanged)
readonly customDefinition = input<boolean>(false);
```

Drives only the action **label** (idle/loading); the availability comes from `generateEnabled`, and the
state from `generateState` — both already existing inputs.

### 3.4 Generation/dedup key (existing, reused)

```ts
// existing, unchanged
function generateKey(subtopicId: string, term: string): string {
  return `${subtopicId}::${(term ?? '').toLowerCase()}`;
}
```

Used by `generatingKeys` (in-flight guard) and `generateStates` (per-key action state), and mirrored by
the backend unique index.
